# Store Master Data ETL with FME: Multi-Country Harmonisation & Data Quality

An independent preparation project that builds a Geo-ETL workflow in **FME Form**:
store location data from two countries is harmonised, joined with business attributes,
validated against business rules and loaded into a GeoPackage. Rejected records are
exported with a clear reason, so the business department can fix them at the source.

> **All data is synthetic.** The company, store names, IDs, postcodes and coordinates are
> fictional and generated by `tools/generate_data.py`. This is not based on any real
> company's data or systems.
>
> Built in an FME Academy lab environment (FME Form) as a learning project.

## 1. Business requirement (fictional)

> *As the expansion department, we need one consistent, validated store master dataset
> for Germany and Romania, so that location analyses and maps are based on reliable data.
> Faulty records must not silently disappear. They should come back to us with a
> clear reason so that we can correct them in the source system.*

### Acceptance criteria

- One target schema and one coordinate system (WGS84) for both countries.
- Every input record ends up either in the valid dataset or in the reject list. Nothing is lost.
- Every rejected record has a rule ID and a readable reason (in German, for the business users).
- A summary shows the share of valid records per run.

## 2. Input data

| File | Content | Particularities |
|---|---|---|
| `data/stores_de.geojson` | 101 German store locations | WGS84 lon/lat; German field names (`filial_nr`, `filialname`, `plz`, `ort`) |
| `data/stores_ro.csv` | 60 Romanian store locations | Coordinates in **Stereo 70 (EPSG:3844)**; numeric store codes; postcodes with leading zeros; diacritics |
| `data/store_attributes.csv` | 161 rows of business attributes | Status, opening date, sales area, format; inconsistent status spelling |

## 3. Business rules

Records are checked in this order. A record is rejected with the **first** rule it fails.

| Rule | Check | Why it matters (business view) |
|---|---|---|
| R1 | Location has business data | A store on the map without status or size can't be used for analysis |
| R2 | Business data has a location | A store that can't be mapped is missing from every location analysis |
| R3 | Store ID is unique | With two records per ID it's unclear which one is correct. Both go back to the business department. |
| R4 | Geometry exists | — |
| R5 | Point lies inside its country (bounding box) | Catches swapped lon/lat, (0,0) and wrong-CRS errors |
| R6 | Mandatory fields filled (name, postcode, status, opening date, sales area) | — |
| R7 | Valid values: status ∈ {open, closed, planned}; sales area > 0; valid date; postcode format (DE 5 digits, RO 6 digits) | — |

**Standardisation (not rejection):** status values are trimmed and lower-cased (`" Open "` → `open`).

## 4. Workflow

```
GeoJSON (DE) ──► AttributeManager (schema) ───────────────────────────┐
CSV (RO) ──► VertexCreator ► CoordinateSystemSetter (EPSG:3844)        ├─► FeatureJoiner (store_id, Inner)
          ► Reprojector (LL84) ► StringPadder ► AttributeManager ──────┘        │        │ UnjoinedLeft/Right → R1/R2
CSV (attributes) ► AttributeTrimmer ► StringCaseChanger ──────────────────────┘
      Joined ► Matcher (store_id) ── Matched → R3
           ► GeometryFilter ── Null → R4
           ► CoordinateExtractor ► Tester (country bbox) ── Failed → R5
           ► Tester (mandatory) ── Failed → R6
           ► Tester (status) ► Tester (area) ► DateTimeConverter ► Tester (postcode) ── Failed → R7
           ► GeoPackage (stores_valid)
All rejects ► AttributeCreator (rule, reason) ► CSV (stores_rejected)
Valid + rejects ► Aggregator ► CSV (quality_summary)
```

## 6. Design decisions

- **Reject both duplicates** instead of keeping the first: the pipeline can't know which record is correct.
- **First failing rule only:** simple and readable for business users. Collecting all failures per record would be the next step.
- **Bounding box instead of country polygons:** fast and sufficient for swapped/zero coordinates, but it wouldn't catch a store placed in a neighbouring country.
- **Repair Overflow disabled** in DateTimeConverter, so impossible dates are rejected instead of silently corrected.
- **WGS84 as target CRS** for a cross-country dataset. Analyses with distances would use a projected CRS per country.
